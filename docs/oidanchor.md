# oidanchor: OpenID Federation Trust Anchor for SimpleSAMLphp

The `oidanchor` module turns a SimpleSAMLphp installation into an
[OpenID Federation 1.0](https://openid.net/specs/openid-federation-1_0.html)
Trust Anchor. It publishes the Trust Anchor's Entity Configuration, registers
subordinates and issues Subordinate Statements about them, resolves trust
chains, and issues Trust Marks and answers status queries for them.

Everything is managed from an admin UI inside SimpleSAMLphp and from a REST
API (`/api/v1/admin/...`).

## Installation

Require the module with Composer from the SimpleSAMLphp root:

```bash
composer require simplesamlphp/simplesamlphp-module-oidanchor
```

Enable it, and the `cron` module that runs its periodic maintenance, in
`config/config.php`:

```php
'module.enable' => [
    'oidanchor' => true,
    'cron' => true,
],
```

Copy `config-templates/module_oidanchor.php` to `config/module_oidanchor.php`
and adjust it (see [Configuration](#configuration)).

### Signing key

The Trust Anchor signs every federation object with one federation key. On
first use, the PEM private key at `signing_key_file` is imported into the key
store in the database; after that, keys are managed (rotated, switched to
another algorithm) from the admin API. Generate an RSA key with:

```bash
openssl genrsa -out oidanchor_module.key 2048
```

The imported key, and every key generated by rotation, lives in the database.
Set `key_store_secret` (at least 32 random characters, for example from
`openssl rand -base64 48`) to encrypt the private keys at rest with
AES-256-GCM; keys stored before the secret was set are encrypted on first
use. Without it the keys are stored as plain JSON, and a warning is logged
whenever a new key is stored. Keep the secret out of the database and its
backups. If it is lost, the stored private keys cannot be recovered: delete
the rows that hold one (`DELETE FROM oidanchor_federation_keys WHERE
private_jwk IS NOT NULL`) and the `signing_key_file` key is imported again.

### Database

The module keeps its state in the database named by `database_dsn`. Tables are
created and migrated automatically on first use, so the database user needs
permission to create and alter tables.

Only **SQLite 3.25 or newer** is supported: the schema setup uses
SQLite-specific statements (`PRAGMA table_info`, `sqlite_master`). Other PDO
databases will not work yet.

### Cron

Interval-based key rotation and the refresh of the Trust Marks the Trust
Anchor publishes about itself run from the SimpleSAMLphp cron module, on the
tag configured as `cron_tag` (default `hourly`). They never run on public
requests, so cron must be set up for that tag. See the cron module's
documentation for invoking it.

### Web server

The Entity Configuration advertises its endpoints as `base_url` plus a path
(for example `https://ta.example.org/federation/fetch`), and federation
clients look for the Entity Configuration at
`https://<entity_id>/.well-known/openid-federation`. Either rewrite those
root-level paths to the module, as `docker/apache-override.cf` does for
Apache, or set the `federation_*_endpoint` options to the module URLs.

## Configuration

All options live in `config/module_oidanchor.php`; the template documents
each one. The most important:

- `entity_id`: the Trust Anchor's Entity Identifier, the `iss` and `sub` of
  its Entity Configuration.
- `base_url`: base for the endpoint URLs advertised in the Entity
  Configuration.
- `signing_key_file`: PEM private key imported into the key store on first
  use.
- `key_store_secret`: secret that encrypts the stored private keys.
- `signing_algorithm`: algorithm the Trust Anchor signs with (default
  `RS256`).
- `verification_algorithms`: algorithms accepted on JWTs from other entities
  (default: every asymmetric algorithm).
- `entity_configuration_lifetime`, `subordinate_statement_lifetime`,
  `trust_mark_status_response_lifetime`: lifetimes in seconds.
- `authority_hints`: superiors, when this Trust Anchor is itself a
  subordinate.
- `resolve`: resolver depth, outbound HTTP timeouts and TLS verification.
- `cron_tag`: cron tag for key rotation and Trust Mark refresh.
- `database_dsn`: PDO DSN of the module database.
- `api_admin_username`, `api_admin_password`: HTTP Basic credential for the
  admin API.
- `api_allowed_origins`: extra origins trusted for session-authenticated API
  writes.

Several values (lifetimes, signing algorithm, RSA key length, rotation
options) can also be changed at runtime through the admin API; a stored value
takes precedence over the configuration file.

`federation_fetch_endpoint_enabled` and `federation_list_endpoint_enabled`
switch those endpoints off: a disabled endpoint answers 404 and is not
advertised in the Entity Configuration.

## Federation endpoints

Paths are relative to the module URL
(`https://<host>/<simplesaml-alias>/module.php/oidanchor`).

| Endpoint                    | Path                                 | Spec  |
|-----------------------------|--------------------------------------|-------|
| Entity Configuration        | `/.well-known/openid-federation`     | 9     |
| Subordinate listing         | `/federation/list`                   | 8.2   |
| Subordinate statement fetch | `/federation/fetch` (alias `/fetch`) | 8.1   |
| Resolve                     | `/resolve`                           | 8.3   |
| Trust Mark status           | `/trust_mark_status`                 | 8.4   |

Signed responses carry `Cache-Control: public, max-age=...` derived from the
token's `exp`. Errors use the specification's JSON error format
(`error`, `error_description`).

The subordinate listing supports the `entity_type`, `trust_marked` and
`trust_mark_type` filters; `intermediate` is rejected with
`unsupported_parameter`. The Trust Mark endpoint (8.5) and Trust Mark listing
endpoint (8.6) are not implemented; see the README.

`/resolve` fetches remote statements on behalf of anonymous callers, so it is
hardened (all in the `resolve` configuration block):

- Responses are reused for `cache_ttl` seconds (default 300).
- Resolutions that miss the cache are limited to `rate_limit` per client IP
  per minute (default 30); over the limit the endpoint answers 429 with
  `Retry-After`.
- Outbound fetches only reach globally routable addresses, so the endpoint
  cannot be used to probe internal hosts. Set `allow_private_networks` only
  for development stacks.
- Fetch and trust chain failures are reported without network detail; the
  detail is logged.

## Admin UI

Log in as the SimpleSAMLphp administrator; the module adds a "Trust Anchor"
entry to the admin menu. The UI covers:

- **Subordinates** (`/admin/subordinates`): register, edit, block, activate
  and delete subordinates, with their JWKS, entity types and metadata policy.
- **Metadata policies** (`/admin/policies`): the federation-wide metadata
  policy per entity type, merged into every subordinate's statement.
- **Trust Mark types** (`/admin/trust-mark-types`) and **Trust Marks**
  (`/admin/trust-marks`): the type catalog, issuing marks to entities and
  revoking them.
- **Resolve tester** (`/admin/resolve`): resolves a trust chain and shows the
  chain, the policy-applied metadata and the signed response.

Every form that changes something carries a per-session CSRF token.

## Admin API

The REST API lives under `/api/v1/admin/` and follows the Federation Admin
OpenAPI contract. Its resources:

- `entity-configuration/...`: the Trust Anchor's own metadata, authority
  hints, additional claims, Trust Marks it holds, metadata policies,
  constraints, lifetimes and published keys.
- `kms/...`: the key store: signing algorithm, RSA key length, rotation
  options and manual rotation.
- `subordinates/...`: subordinates, their JWKS, metadata, metadata policies,
  constraints, additional claims, statements and history.
- `trust-marks/...`: Trust Mark types, issuers, owners, issuance specs and
  their subjects. Setting a subject `active` issues its mark; any other status
  revokes it.

Requests authenticate either with HTTP Basic (`api_admin_username` /
`api_admin_password`; this is what a gateway uses) or with the SimpleSAMLphp
admin session. A session-authenticated `POST`, `PUT`, `PATCH` or `DELETE` must
come from this origin (checked with the `Origin` / `Sec-Fetch-Site` headers),
which blocks cross-site request forgery. Errors are JSON objects with `error`
and `error_description`.

## Keys and Trust Marks

- **Key rotation** is manual (`POST /api/v1/admin/kms/rotate`) or
  interval-based (from cron). The old key stays published for the rotation
  `overlap`, in seconds. The default overlap is 0, which unpublishes it at
  once, so statements it signed stop verifying; set an overlap of at least the
  longest statement lifetime.
- **Switching the signing algorithm** keeps the key when it can serve the new
  algorithm (for example RS256 to PS256) and rotates to a new key otherwise.
- **Trust Marks** are issued from an issuance spec per Trust Mark type; the
  type catalog in the admin UI keeps the spec's descriptive fields in sync.
  A mark's status (`active`, `expired`, `revoked`) is answered by
  `/trust_mark_status` from the issued-marks registry.
